# Architecture

## Goals that shaped the design

1. **Fast on a phone over an average connection.** A marketing site for an AI company is judged on speed. Target: LCP ≤ 2.5 s, INP ≤ 200 ms, CLS ≤ 0.1 in field data.
2. **Readable by crawlers and answer engines without JavaScript.** Every word, number and FAQ answer is in the HTML at build time.
3. **One source of truth for company facts**, so the entity that search and AI engines see is consistent on every page.
4. **Cheap to host and hard to break.** No server to patch, no database, no plugins. The only server code is the CMS admin (below), which public pages never touch.

## Rendering model

```
 Markdown + .astro + TypeScript ──► astro build ──► .vercel/output/
                                                      ├─ static/   every public page as plain HTML, CSS, small JS
                                                      └─ functions/ one function for /keystatic and /api/keystatic
                                                         │
                                                         ▼
                                              Vercel edge network
```

- **Static site generation.** Astro 7 with the `@astrojs/vercel` adapter. Every public route is prerendered to HTML at build time. The adapter exists for two reasons only: the Keystatic CMS routes (`/keystatic`, `/api/keystatic`) run on demand as a Vercel function, and `staticHeaders: true` sends each page's Content Security Policy as a real HTTP header.
- **Zero framework JavaScript.** Interactive pieces (calculators, booking form, mobile menu, the animated queue) are small TypeScript modules in `<script>` tags. Astro bundles and hashes them; pages without them ship no JavaScript except the Google tag.
- **Progressive enhancement.** Calculators render their default result on the server, so the page is complete before any script runs. Scripts only recalculate when inputs change.

## Routing

File-based routing under `src/pages/`:

- Static pages map one-to-one to files (`msp.astro` → `/msp/`).
- `services/[slug].astro` generates four pages from `lib/serviceDetails.ts` via `getStaticPaths`.
- `[slug].astro` at the root generates one page per article in `content/insights/`. Articles live at the root so URLs from the old WordPress site keep working without redirects.
- `insights/[topic].astro` generates one hub page per topic in `lib/topics.ts` (`/insights/msp-automation/` etc.).
- Internal links between articles, services, calculators and audience pages are generated from article frontmatter; see [CONTENT-AND-SEO.md](CONTENT-AND-SEO.md#internal-linking).
- `build.format: 'directory'` plus `trailingSlash: true` in `vercel.json` keep canonical URLs consistent (`/msp/`). Astro's own `trailingSlash` is `'ignore'` because the Keystatic admin uses client-side URLs without a slash; public pages are unaffected.
- `case-studies/[slug].astro` and `case-studies/[...index].astro` generate case-study pages from `content/case-studies/`. The index page and its footer link appear only once at least one case study is published.
- Legacy URLs (`/about-us/`, `/contact-us/`, `/blog/`) are handled twice: as real 301s in `vercel.json` (with `.htaccess` and `_redirects` equivalents for other hosts), and as static meta-refresh fallbacks generated by `astro.config.mjs`.

## Data flow

```
src/site.config.ts ─┬─► Header / Footer / About / Book (facts, nav, offices)
                    ├─► lib/schema.ts ─► Base.astro JSON-LD graph on every page
                    └─► formEndpoint / bookingUrl (from PUBLIC_* env vars at build time)

src/content/*  ──► content.config.ts (zod schemas) ──► [slug].astro, insights/index.astro, rss.xml.ts, privacy-policy.astro

lib/calc.ts ──► calculator pages (server-rendered defaults + client recalculation)
            └─► tests/calc.test.ts

calculator page ──(sessionStorage via lib/handoff.ts)──► /book/ ──(POST JSON)──► PUBLIC_FORM_ENDPOINT
                                                                  └─(fallback)──► mailto:
```

### Calculator → booking handoff

1. When a visitor changes a calculator input, the page saves a short summary (inputs and key results) to `sessionStorage` under `moksh_calc`. Defaults are never saved, only values the visitor touched.
2. `/book/` reads it and shows an "Attach my calculator results" box.
3. On submit the summary is added to the JSON payload as `calculator`.
4. Storage access is wrapped in `try/catch`; if storage is blocked the form simply doesn't prefill.

### Booking form

- Client-side validation with specific error messages (missing name, invalid email, team type).
- A hidden honeypot field (`company_website`) drops bot submissions silently.
- With `PUBLIC_FORM_ENDPOINT` set: `fetch` POST of JSON, success panel, optional link to `PUBLIC_BOOKING_URL`, and a `generate_lead` analytics event.
- Without it: the form opens the visitor's email app with the request pre-filled and tells them what happened. This is a fallback, not a production setup.

## Analytics

`Base.astro` loads the Google tag carried over from the old site (`GT-PLWBBHHT` Site Kit tag and `AW-17581749958` Google Ads). The library is **deferred** until the visitor's first interaction (scroll, tap, key press) or 5 seconds after load, whichever comes first; calls made before that are queued in `dataLayer` and sent when it loads. Measured on the live site, loading it eagerly cost ~370 KB, ~0.9 s of main-thread blocking and dropped Lighthouse mobile performance from 96 to 53. Trade-off: a visitor who leaves within 5 seconds without interacting is not recorded.

Events fired by `lib/handoff.ts → track()`:

| Event | When |
| --- | --- |
| `calculator_start` | First input change on a calculator |
| `calculator_book_click` | "Discuss these numbers" clicked |
| `form_start` | First input on the booking form |
| `generate_lead` | Booking form sent successfully |

Map `generate_lead` to a conversion action in Google Ads.

## Performance decisions

- Self-hosted WOFF2 fonts (Archivo variable, IBM Plex Sans, IBM Plex Mono), two of them preloaded, with metric-matched fallbacks to avoid layout shift.
- No images in heroes. Every illustration is HTML/SVG drawn with CSS, so it is sharp at any size and costs a few kilobytes.
- Animations use `transform` and `opacity` only and never move layout. The queue panel swaps text in place rather than inserting rows. Scroll reveals move content but never hide it.
- Everything respects `prefers-reduced-motion`.
- Looping animations pause when off screen or when the tab is hidden: mark the element with `data-loop` and `Base.astro` toggles `.anim-paused` on it with an IntersectionObserver.
- Long-term immutable caching for `/_astro/*` and `/fonts/*` (hashed or versioned files).

## Security

- No user data stored by the site. The only server code is the Keystatic API route, which signs in through GitHub and commits to this repository.
- **Content Security Policy** (`security.csp` in `astro.config.mjs`). Astro hashes every script it emits and lists the hashes in the policy, so any inline script Astro didn't generate is blocked. Consequences:
  - Never use `<script is:inline>` or `define:vars`; pass data through a `data-` attribute or `<meta>` and read it in a bundled `<script>` (see the Google tag loader in `Base.astro`).
  - A new third-party host (analytics, embed, form service) must be added to the matching list at the top of `astro.config.mjs`, or the browser blocks it. The form service origin is added automatically from `PUBLIC_FORM_ENDPOINT`.
  - Styles allow `'unsafe-inline'` because components set CSS custom properties through `style=""`.
  - The policy is off in `astro dev` (Astro doesn't support CSP there); check CSP changes on a production build.
  - `scripts/vercel-csp-routes.mjs` runs after the build to fix two adapter bugs: CSP routes didn't match URLs ending in `/`, and they stopped Vercel from applying the later header rules.
- JSON-LD is serialised with `<` escaped as `\u003c`, so a `</script>` inside content can't end the block early.
- Security headers (`vercel.json`): `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy`, HSTS.
- The booking form sends data only to the endpoint configured in `PUBLIC_FORM_ENDPOINT`.
- Calculator inputs stay in the browser unless the visitor attaches them to a booking.

## Extending

- **New article:** add a Markdown file to `src/content/insights/` with the required frontmatter. It appears in the index, the RSS feed and the sitemap automatically.
- **New service page:** add an entry to `services` in `site.config.ts` and its copy in `lib/serviceDetails.ts`; optionally add a scene and map it in `services/[slug].astro`.
- **New calculator:** add pure functions and tests to `lib/calc.ts` / `tests/calc.test.ts`, metadata to `lib/tools.ts`, and a page under `pages/tools/` using `ToolPage.astro`.
- **New case study:** add it in the CMS at `/keystatic` (see [CONTENT-AND-SEO.md](CONTENT-AND-SEO.md#editing-in-the-cms)).
- **Server features** (for example an AI opportunity-snapshot form that calls the Claude API): add an API route with `export const prerender = false`. The adapter is already installed; the rest of the site stays static.
